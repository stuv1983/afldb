## 4. Principal selection and binding

Evidence read: ../metadata-repair-v5-discovery/discovery.sh and discovery.stdout.log (read-only through the existing afldb_backup credential, catalog privilege functions only, no secret printed; the script prints role/host/port/database and whether a password component is present). Findings from that output:
- Roles able to UPDATE data_edits.note: afldb_owner, pg_write_all_data, postgres. Login roles able to do both writes: afldb_owner and postgres only. afldb_app/afldb_backup have no write; afldb_auth and afldb_import (the normal admin path) hold INSERT only, so none of them can perform the repair or take the inherited lock set.
- afldb_owner: LOGIN, not superuser/createrole/createdb/replication/bypassrls, no memberships either way, no role settings, owns the database, schemas and all 28 lock-set relations. data_edits ACL and sequence ACL text, which principal.sql pins exactly, match the discovery output character for character. The key AFLDB_PROD_DATABASE_URL exists once in the arm-only .env (mode 600 owner arm) and names afldb_owner@localhost:5432/afldb_prod; tools/maintenance/00_install_postgres_prod.sh:230 shows the install deliberately writes that key.
- I statically compared principal.sql against every discovery fact (attributes, memberships, settings, owners, ACLs, writer set) and found each one satisfied, so the prerequisite should not false-refuse; if it does, it fails before the marker.

Conclusion: afldb_owner is justified as the narrowest existing role able to do the repair without new grants, credentials, sudo or authentication change. It is not a "normal application path" role, because no role has note-UPDATE except the owner and the superuser. See F-007 for the residual breadth.

Binding exactness: identity.sql requires database name, OID 66668, system identifier 7674454702926115004 and session_user = current_user = afldb_owner. principal.sql then requires role attributes, no memberships or settings, database owner and all 28 relations plus the id sequence owned by the role, the exact data_edits and sequence ACL text, no column ACL, and the exact set of non-superuser roles able to update note (afldb_owner plus a memberless pg_write_all_data). It never accepts a role merely because it holds a privilege. Real-role tests on a private cluster refuse an importer role, a superuser, a superuser using SET ROLE, a granted membership, SET ROLE to another user, CREATEROLE/CREATEDB/BYPASSRLS, a role setting, four privilege perturbations and five ownership perturbations (validate-pg.cjs:272-321). A different database or cluster must reproduce the OID and system identifier, so only a physical copy of production could pass; the host gate (hostname afldb-prod, user arm) and the pinned localhost:5432 endpoint further narrow that.

## 5. Credential safety

- run.cjs never reads a credential, never receives one, and passes only fixed non-secret constants (the .env path, key name, principal, endpoint) as shell words. The ssh argv holds the remote script text and the SQL travels on stdin. Neither contains a credential. transport.sh runs on the host.
- transport.sh requires a regular, non-symlink, readable file with `600 arm`, exactly one `^AFLDB_PROD_DATABASE_URL=` line, no CR or backslash, a strict URL regex (no parameters), and exact equality of user, host, port and database with the pinned values before the password is even decoded. Every refusal prints a fixed reason string, never a value, and clears the variable first. The password is decoded with the builtin printf into a shell variable, never passed to an external command, and is exported only as PGPASSWORD. I looked for injection or bypass through the user/host/db fields (they are compared as strings and never evaluated), the password (a literal backslash in the file is refused; percent-decoded bytes are held as data and never re-evaluated) and the key (a pinned constant). I found none.
- Environment clearing: every exported name is unset (a readonly one fails closed), a fixed allowlist is exported, and the exported set must equal the allowlist exactly or PGPASSWORD is unset and the run stops. The real psql process observed in validation had exactly the allowlist plus platform-added SHLVL and PGSYSCONFDIR, no inherited decoy, /proc environ mode 400 and an argv scan across all processes that found no credential (validate-pg.cjs:116-139, 341-365).
- Retained logs: the wrapper retains stdout/stderr of observation, prerequisite and execution; none can contain the password because it is never printed and psql does not echo it. In the retained validation evidence, my independent scan of all 8 evidence files for the fixture password prefixes, SCRAM verifiers, PASSWORD statements, PGPASSWORD values and DSN strings found nothing (only the literal word PGPASSWORD in test names).
- Residual: see F-012 (environment variable, standard libpq mechanism).

## Findings

F-006 (prior, LOW): CLOSED by supersession in v5, see section 7.

- F-007 LOW, non-stopping. principal.sql:1-4, README.md:21-32, ../metadata-repair-v5-discovery/discovery.stdout.log (I316_DISC_WRITE_CAPABLE, afldb_owner candidate). afldb_owner owns the database and every protected table and can run DDL, TRUNCATE, DELETE and GRANT; the repair needs two writes. Failure scenario: a defect in the pinned SQL or a changed stdin would execute with owner power. Mitigations: the SQL is hash-pinned and reviewed, supplied by Node on stdin, the exact two-write stream is checked above, no existing role is narrower, and the package adds no grant. The package states this breadth itself. This is the one judgement call in the package: if the owner reads "suitable existing role" as excluding the schema owner, the only alternative is owner adjudication, since discovery shows no other non-superuser could do the repair. I treat it as accepted by the owner's own rule (OWNER-RULING.md:109, 118).
- F-008 LOW, non-stopping. repair-body.sql:12. The permanent audit record names the model identifier `claude-opus-5-5`. I cannot verify that this is the model of the session that will launch run.cjs. A wrong value would make an immutable audit field inaccurate; correcting it after this review would require re-review. The primary should confirm the identifier against the launching session before execution; no other part of the literal is in doubt (Claude Code, afldb_owner via the existing .env credential, no sudo).
- F-009 LOW, non-stopping. run.cjs:163-171 with remoteScript at 54-57. The write session re-runs the host gate, credential checks and connection after the marker, so a stop there (for example a new process or a changed credential file in the seconds between the sessions) consumes the attempt although no database transaction was submitted. This is the conservative side and matches "after the marker any outcome consumes the attempt", but it is narrower than the owner's wish that local transport prerequisites not consume the attempt. No safety consequence; the cost is an owner adjudication round trip.
- F-010 LOW, non-stopping. operational-host.sh:1-88, run.cjs:54-62,103,163, validate-pg.cjs:403-407. The off-production tests prove only that the host gate refuses a non-production hostname. They do not exercise the gate's PASS path, the brace-group stdin restoration into psql, the real ssh.exe argv carrying the ~12 KB quoted `bash -c` script from Windows to arm's login shell, the PPID/self exclusion of the script's own `i316` text, or `localhost` resolution (the transport tests use 127.0.0.1). The VM wrapper replays hand-built psql output, not real psql output. Failure scenario: any of these mismatches fails closed in the read-only prerequisite session before the marker, so the exposure is an unplanned STOP, not a write.
