## 5. ISSUE-280: mailbox, recipient, token lifecycle and how the prefetch is demonstrated

### 5.1 Facts to establish first (read-only), and what they decide
Run `acceptance\remote\env-readonly.sh` (prints only these values: `AFLDB_ENV`, `AFLDB_BASE_URL`, `AFLDB_BETA_GATE`, `AFLDB_INDEXING`, `AFLDB_WORKERS`; and for the
mailer only whether each `AFLDB_SMTP_*` key is set). It decides three things: (a) **can DEV send mail?** If `AFLDB_SMTP_HOST` is unset, `sendEmail` fails and the link is
**only logged** (non-production): the journal line `[beta] magic link for <email>: <link>` carries the credential, so no email leaves the host and the real-mailbox
check (below) cannot be done without a settings change; (b) **which origin the link carries** (`AFLDB_BASE_URL`; the link is `${AFLDB_BASE_URL}/beta/verify?token=...`; if the browser
cannot reach that origin, replace only the origin, the token is the same); (c) that the gate is on (the page is public either way: `/beta` is a public prefix).

### 5.2 Recipient and mailbox (D-280-1)
- **Recipient:** an address that is **already on DEV's allowlist and not revoked** (`/admin/access`, read-only look). A new allowlist entry is a write (a row and an audit event) and needs its own approval. Working assumption, **not verified**: the owner's own mailbox (`stuart.villanti@gmail.com`) if it is listed.
- **What the mailbox proves.** The runbook's §14 item 2 names "a prefetching mailbox". A mailbox with no link-scanning gateway (a Gmail account is **not known** to pre-fetch links; treat it as having none unless a prefetch is seen) cannot show the original defect. The runbook allows noting that the mailbox has none (§17.3 item 3). ### 5.3 Token lifecycle (what each step writes)
| Step | Writes |
|---|---|
| Request a link on `/beta` ("My email is on the list", rate limit 5 per 15 min per IP) | `beta_login_tokens` +1 (email, **sha-256 of the token only**, `expires_at = now()+30 min`); audit `beta.magic_link_issued {email, delivered}`; one email, or the journal line when delivery fails |

## 6. ISSUE-279: the separate temporary settings window

**Correction to the parked procedure (runbook §19 step 2 said "restart").** `AFLDB_INDEXING` is **read at build time** (`docs/deployment.md` §10; `docs/production-cutover.md` Step 10: "a restart alone will not
take"). The sitemap is produced by `generateSitemaps()` and cached with `revalidate = 86400`, and every prerendered page bakes its robots metadata in at build. `src/lib/indexing.ts` also returns false
while `AFLDB_BETA_GATE=on`, so both keys must change **in the same build**. A restart with the new `.env` would still serve the empty, already-built sitemap and could not pass. **The window is therefore
two builds** (open and close), each about 10 minutes and each a restart. This is a larger change than the runbook described and is why 279 is a separate decision.

### 6.1 Exactly what changes (`acceptance\279\remote\window-279.sh`, sandbox-tested 23/23, never run on a host)
| Step | Action |
|---|---|
| Before | `env-readonly.sh` (current values), `gate.sh`-class preconditions (the script refuses unless HEAD = TARGET on `main`, clean tracked tree, healthy service, outside 02:00-03:15 and 04:40-05:35, next afl_api settle at least 60 minutes away) |
| `open <TARGET>` | back `.env` up (mode 600, `.env.bak-279-<stamp>`), record its sha-256 and the original `AFLDB_INDEXING` and `AFLDB_BETA_GATE` (line counts and values), set **exactly** `AFLDB_INDEXING=on` and `AFLDB_BETA_GATE=off`, `npm run build`, kill MainPID (systemd respawns), wait for health |
| `check` | fetch `/robots.txt`, `/sitemap.xml`, `/sitemap/0.xml`, `/sitemap/1.xml` from `127.0.0.1:3100`, keep the raw bodies, print counts. **Pass** = `/sitemap/0.xml` has at least one `<url>` and robots no longer disallows everything |
| `close` | restore `.env` byte-for-byte from the backup (sha-256 equals the recorded original, else exit 4), `npm run build`, restart, then verify robots says `Disallow: /`, the index lists no `<sitemap>`, `/sitemap/0.xml` has no `<url>`. Exit 0 only if all hold |

### 6.2 Exposure implications (stated, not hidden)
- **Gate off** for the window: any client that can reach `10.0.40.100:8090` reads the public site without a beta cookie. DEV is a LAN host; **whether it is reachable from outside the LAN (port forward, tunnel) has not been verified here**: the owner confirms it is not before D-279-1. Admin pages still require their own session.
- **Indexing on:** `robots.txt` stops disallowing, pages built in the window carry `index,follow`, and `/sitemap.xml` lists URLs on `AFLDB_BASE_URL` (the DEV origin, not a publishable one). No crawler can reach a private address, but a copy of those pages with `index` metadata sits in the build until the **closing** build replaces it; that is why the close is a rebuild and not a restart.
- **Cost:** the DEV build identity changes twice; the per-worker page caches reset at each restart; roughly 20 minutes of builds plus restarts of about 10-20 seconds each; the nightly must not overlap (the script refuses within 60 minutes of it).
- **Failure modes:** a failed opening build leaves `.env` in the OPEN state while the old build still serves: run `close`. A failed closing build leaves `.env` restored and the OPEN build serving: **retry `close`**; do not walk away. Exit 4 (restore verification failed) is a stop.
- **PROD:** nothing here touches PROD, and indexing must not be enabled on PROD as part of this.

### 6.3 Restoration verification (the evidence to keep)
`close`'s own log plus: `env-readonly.sh` afterwards (values equal the recorded originals), `.env` sha-256 equal to the recorded original, `/robots.txt` anonymous = `Disallow: /`, `/sitemap.xml` empty, a page's source shows `noindex`, `/api/health` ok, the new BUILD_ID recorded.

### 6.4 Closure
`AFLDB-ISSUE-279` closes DEV-scoped when `check` passes **and** the close verification passes. If the owner prefers not to touch DEV settings, the alternative is the supplementary local build against a read-only `afldb_test` connection
(the ISSUE-303 §19 recipe) with the same two keys, inspecting `.next/server/app/sitemap/0.xml.body`: useful evidence, but it is **not** the runbook's DEV check and does not close the issue by itself.
