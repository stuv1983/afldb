### 5.3 Token lifecycle (what each step writes)
| Step | Writes |
|---|---|
| Request a link on `/beta` ("My email is on the list", rate limit 5 per 15 min per IP) | `beta_login_tokens` +1 (email, **sha-256 of the token only**, `expires_at = now()+30 min`); audit `beta.magic_link_issued {email, delivered}`; one email, or the journal line when delivery fails |
| Scripted or real **GET** of the link (any number) | **nothing**: no table read, no audit, no cookie (this is the invariant being accepted) |
| Reader presses **Sign in to the beta** (POST, limit 20 per 15 min per IP) | `beta_login_tokens.used_at`; audit `beta.magic_link_verified`; the `afldb_beta` cookie; redirect to `/` |
| Replay of the same link | page renders; POST finds no unused row; redirect to `/beta`; **no audit row** (by design) |
| Expiry | after 30 min an unused token is dead; rows are never deleted by any job, so each issuance leaves one `beta_login_tokens` row (hash only) |

### 5.4 The procedure
**A0. Optional control on PREV, before the deployment (D-280-1 says whether).** Request a link; read the token (journal or email); run
`python -I acceptance\280\prefetch-sim.py --base http://10.0.40.100:8090 --expect burn` (token via the hidden prompt). Expected on PREV: the **first** GET is a 3xx **with the `afldb_beta`
cookie** (the scanner is admitted and the token spent) and later GETs go to `/beta`; the click then bounces to `/beta`; `/admin/audit` shows `beta.magic_link_verified` **before** any human click. That is the defect reproduced and the incidence evidence
the runbook said could not be collected. It costs one token row, two audit rows and (if mail is on) one email.

**A1. After the deployment (the acceptance), new token.**
1. Request a link for the D-280-1 recipient; record the time. Token source: the email, or when DEV cannot send, the journal (the operator reads it; `acceptance\remote\journal-280.sh <since as YYYYMMDDTHHMMSS>` (the form `Invoke-Remote` accepts; the first pack documented a spaced time that it rejects) prints a **redacted** view for the record and never the credential; it exits 4 with every counter UNKNOWN if the journal could not be read completely, including a permission diagnostic that came with exit 0).
2. `python -I acceptance\280\prefetch-sim.py --base http://10.0.40.100:8090 --expect confirm` (token via hidden prompt): 3 GETs with scanner-like User-Agents on fresh connections and one HEAD. **Pass** = every GET `200` with "Confirm sign-in", **no `afldb_beta` cookie, no Location**; HEAD `200`. The token is not printed (only a hash prefix), and neither is any token-bearing redirect URL or exception text: a Location is reduced to its path and everything printed is scrubbed.
3. `/admin/audit`: `beta.magic_link_issued` present, **no** `beta.magic_link_verified` yet.
4. In the browser open the same link at 1280x800 and again at 390x844 (separate captures; light and dark if the owner's browser is on dark): images **V-280-1** (desktop) and **V-280-2** (mobile), URL bar visible, showing the one-button page. Press **Sign in to the beta**: lands on `/`, signed in (image **V-280-3**).
5. `/admin/audit`: now exactly one `beta.magic_link_verified` for the recipient.
6. Open the same link again and press the button: redirected to `/beta`, **no** new `verified` row (replay refused).
7. If a real prefetching mailbox is used, repeat steps 1, 3-6 *without* the script and state whether the gateway touched the link (Caddy log) and that the click still worked.
8. Journal check (§7): no `syntax error`, `unhandled`, `ECONNREFUSED` or digest line.

## 6. ISSUE-279: PARKED. The window script is withdrawn as UNSAFE; there is no executable procedure in this revision

**Original acceptance criteria (R279 §14 item 2), preserved unchanged and not weakened:** on DEV with `AFLDB_INDEXING=on` (and the beta gate off), `/sitemap/0.xml` must contain at least one `<url>` (the `/sitemap.xml` index lists the segments; a sample of the others, e.g. `/sitemap/1.xml`, would strengthen it). The DB-free tests and any local build are supplements and do not close the issue. ISSUE-279 stays OPEN.

**Correction to the parked procedure (still true; runbook §19 step 2 said "restart").** `AFLDB_INDEXING` is **read at build time** (`docs/deployment.md` §10; `docs/production-cutover.md` Step 10: "a restart alone will not take"). The sitemap is produced by `generateSitemaps()` and cached with `revalidate = 86400`, and every prerendered page bakes its robots metadata in at build. `src/lib/indexing.ts` also returns false while `AFLDB_BETA_GATE=on`, so both keys must change **in the same build**. A restart with the new `.env` would still serve the empty, already-built sitemap and could not pass. A real check is therefore a two-build window (open and close), which is why it is a separate, larger decision.

**Status of the script `window-279.sh`: UNSAFE for operational use.** It is moved out of the executable tree to `parked-unsafe\279\` (renamed `window-279.sh.UNSAFE-NOT-FOR-USE`, with a first-line refusal that exits 99), excluded from every step of this procedure, and **its earlier "sandbox-tested 23/23" statement is withdrawn**: those 23 cases tested helper functions against stubs and did not exercise the failure modes below. The review of the first pack found three classes of defect; `parked-unsafe\279\UNSAFE.md` lists what reading the script shows for each:
- **false successes:** a restart or a health probe can pass against the old process; the closing checks pass on empty or error bodies;
- **missing host and build verification:** nothing proves the script is running on the DEV host, or that the build being served is the one just built or just closed;
- **a recovery gap:** a failed or refused step can leave the gate off and indexing on with no safe, unattended way back, and `close` refuses to run in exactly the periods when an operator may need it.

These need a **separate correction and a separate review before the script is used** (a new script, not an edit of this one); until then D-279-1 does not exist as a decision, no DEV settings window should be opened by any means, and the alternative of a supplementary local build against a read-only `afldb_test` connection (the ISSUE-303 §19 recipe) is useful evidence but is **not** the runbook's DEV check and does not close the issue. PROD: nothing here touches PROD, and indexing must not be enabled on PROD as part of this.
